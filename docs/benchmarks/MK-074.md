# MK-074: 포지셔닝·라이선스 초안과 로컬 벤치

라이선스(MK-077)는 `Apache-2.0`으로 확정됐으며,
`THIRD_PARTY_NOTICES.md`는 설치된 cargo-deny와 Cargo.lock으로 자동 생성한 macOS 의존성 고지다.
원문 누락·잠정 라이선스 예외 검토는 [배포 전 체크리스트](../licensing/README.md)에 남겼다.

## 재현

```sh
perl -e 'alarm shift; exec @ARGV' 300 cargo build --release --locked --bins
python3 docs/benchmarks/mk074.py --rounds 3 --settle 5 --output /tmp/mk074.json
python3 -m unittest discover -s docs/benchmarks -v
python3 docs/licensing/generate_notices.py --check
```

Krill은 매회 새 임시 HOME·상태·작업 폴더에서 실행한다. 사용자 전역 설정은 바꾸지 않는다.
`/bin/sh`를 로그인 셸로 지정하고 AI 에이전트는 띄우지 않는다. 워크로드는 첫 실행 창·기본 세션이며,
10개 활성 터미널·실제 에이전트 작업·장시간 메모리 게이트를 대표하지 않는다.

기동 시간은 `Popen` 직전의 단조 시각부터 해당 PID 소유의 on-screen layer-0 창(가로·세로 각각 100px 이상)이
WindowServer 메타데이터에 처음 나타날 때까지다. 20ms 폴링 사이에 `ps`도 실행하므로 관측 지연이 포함된다.
첫 픽셀 렌더·셰이더 컴파일 완료·터미널 연결·10세션 마지막 화면 준비 시간을 뜻하지 않는다.
매회 새 프로필을 쓰되 OS 파일 캐시를 비우지 않아 디스크 cold start도 아니다.

창이 나타난 뒤 5초 안정화하고 `proc_pid_rusage(RUSAGE_INFO_V0).ri_phys_footprint`를 읽는다.
Krill 앱·holder·krilld만 합산하고 셸·에이전트는 제외한다.
정리할 때는 이 실행이 띄운 프로세스 트리의 PID·프로세스 시작 시각을 기록해 재사용된 PID에 신호를 보내지 않는다.

**Orca는 새로 실행·재시작·활성화·종료하지 않는다.** 현재 실행 중인 설치 앱·Helper·Terminal Host만
`ps`로 열거해 `footprint -p <pid> -f bytes --noCategories`와 `ps rss`를 읽는다.
에이전트·셸·일시적인 Orca CLI는 제외한다. 프로세스가 도중에 종료되거나 읽기가 실패하면
원자료의 `skipped_pids`에 남긴다. Orca 기동 시간은 **미확인**이다.

현재 Orca는 여러 프로젝트·워커를 호스팅한다. Krill의 새 실행 창과는 워크로드가 다르며,
메모리 비율·절감률이나 기동 속도 우열을 주장할 수 없다. 프로세스별 footprint 단순 합계는
공유 메모리를 중복 계산할 수 있고, RSS는 footprint와 다른 지표이므로 같은 열에서 비교하지 않는다.

## 생존 근거와 한계

실제 release GUI SIGKILL·재실행 테스트(MK-031)는 독립 사이클 3/3회에서
세션 PID·데몬 instance 유지, 회당 408,058바이트·SHA-256 완전 일치를 기록했다.
MK-064는 데몬 업그레이드·krilld 크래시·1GiB 폭주 및
10세션 24에포크 가속 소크의 근거다. 기존 release 소크의 데몬 합계 47.39MiB는 앱을 제외한 수치이며,
24에포크는 실제 24시간이 아니다. README는 이 기존 기록과 이번 측정을 구분한다.

앱 크래시의 링·세그먼트 범위 무손실 보장과 krilld 크래시의 미기록 출력 손실 가능성을 구분한다.
holder·krilld 동시 소실·재부팅 때 프로세스는 죽고 마지막 디스크 기록만 읽기 전용 복원된다.
정확한 보장 범위는 [ARCHITECTURE §4.1](../ARCHITECTURE.md#41-장애별-보장-범위-규범)을 따른다.
