# Demock Playbook (프로덕션 가짜 성공 및 삼킨 예외 제거)

## Trigger

`drive` 완료 직후 자동 후속 단계로 실행하거나, 사용자가 코드베이스의 가짜 성공, 삼킨 예외, 프로덕션 테스트 더블, 미구현 플레이스홀더 점검을 요청했을 때 `afk` 기어로 실행한다. 완료 후 [verify.md](verify.md)로 이어진다.

## Steps

1. **스캔 대상 확정 및 실행.**
   - `drive` 후속 체인으로 진입한 경우 `.krig/base-sha` 대비 변경 및 신규 생성된 파일 목록을 스캔 대상으로 넘긴다(삭제된 파일은 제외).
   - 단독 `demock` 호출인 경우 사용자가 지정한 경로(생략 시 현재 저장소 `$PWD`)를 넘긴다.

```bash
node "<SKILL_DIR>/scripts/scan.mjs" --json <대상_경로...>
```

2. **4분류 트리아지.** 종료 코드가 `3`(후보 발견)이면 각 후보를 실제 문맥과 대조해 아래 네 가지 중 하나로 분류한다.
   - **(a) 실경로 테스트 더블 (`test-double-in-prod`)**: 프로덕션 파일에 들어간 `jest.fn`, `sinon`, `unittest.mock`, 하드코딩 스텁 응답.
   - **(b) 거짓 성공 및 느슨한 보안 가드 (`swallowed-error`, `permissive-guard`)**: 예외를 잡고 `true`나 빈 결과를 반환하거나, 시크릿/서명 누락 시 통과시키는 분기.
   - **(c) 미구현 플레이스홀더 (`placeholder`)**: 구체 구현체의 `NotImplementedError`, `todo!()`, `throw new Error("TODO...")`.
   - **(d) 의도된 비치명 폴백**: 캐시 워밍업 실패 무시처럼 비즈니스 계약상 정상이고 관측 가능한 경우.
3. **실패 테스트 선작성 및 정직한 교정.**
   - (a), (b), (c)에 해당하는 모든 결함은 먼저 거짓 성공이나 누락이 드러나는 실패 행동 테스트를 작성해 깨지는 것을 확인한다.
   - 이후 실제 의존성 어댑터 연결 또는 명시적 에러 전파/거부로 고쳐 테스트를 통과시킨다.
   - (d)로 판정한 정당한 예외 블록만 `try` 직전 줄 또는 `catch`/`except` 블록 내부에 구체적 사유를 적은 `// demock: allow <사유>` 또는 `# demock: allow <사유>` 주석을 남긴다.

## Rules

- 테스트 통과만을 목적으로 예외를 조용히 삼키거나 기본 성공값을 반환하는 수정은 금지한다.
- 외부 서비스 장애나 인증 시크릿 누락은 항상 호출자가 분기할 수 있는 명시적 오류로 드러나야 한다.

## Verification

- 교정 후 다시 `node "<SKILL_DIR>/scripts/scan.mjs" <대상_경로...>`를 실행해 종료 코드 `0`이 나오는 것을 직접 확인한다.
- 새로 추가한 실패 재현 테스트를 포함한 테스트 스위트가 종료 코드 `0`으로 통과하는지 확인한다.
